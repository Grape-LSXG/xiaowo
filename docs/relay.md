# 异地联机：为什么最终选 MQTT 中转

## 结论

**点单端不需要装任何别的软件，配对一次，永久有效。**

实现方式：双方约定一个 **6 位房间码**，都订阅同一个公共 MQTT topic。
不需要账号、不需要服务器、不需要 Tailscale。

真机实测通过：

```
接单端「最近一单」
  💗 来自 猫猫        10-22 08:44
  🫂 要抱抱  ×2  ❤10
  合计 ❤10 · 接单的人最好看
```

而当时接单端显示 `🛰 Tailscale：未连接` ——
**这一单和 Tailscale 完全无关，是走 MQTT 过来的。**

---

## 走过的弯路（以及为什么放弃）

| 方案 | 卡在哪 |
|---|---|
| SakuraFrp 穿透 | 服务端为合规**拦截明文 HTTP**（501），TCP 隧道又不终止 TLS，绕不过去 |
| Tailscale | 能用，但要**另装一个 App**、要账号；用户明确说不想再装 |
| 内置 Tailscale | +24 MB 体积、要自带 VpnService、**仍然要 Tailscale 账号**（见 `tailscale-embedded.md`） |
| 局域网 UDP 广播 | 只在一个 Wi-Fi 下有效，异地必然失败 |

MQTT 中转把上面全部绕开了：**零安装、零账号、零服务器、零第三方依赖**。

---

## 三种通路与优先级

App 里按顺序尝试，前一个失败才走下一个：

1. **局域网直连** —— 同一个 Wi-Fi 时最快（UDP 8766 自动发现）
2. **Tailscale / 手填 IP** —— 有虚拟内网时，也是直连
3. **MQTT 中转** —— 异地兜底，最慢但最通用

三者共用同一套 HTTP 处理器，所以爱心、通知、去重逻辑天然复用。

## 协议与实现

`core/Mqtt.java` —— 手写 MQTT 3.1.1 客户端，只做需要的那部分：

```
CONNECT / CONNACK / SUBSCRIBE / SUBACK / PUBLISH(QoS0) / PINGREQ
```

QoS0 = "最多一次"，不保证送达。够用，因为前面还有局域网直连，
而且订单本身带 id、接单端会去重。

`core/Relay.java` —— 配对与封装：

```json
{"relayFrom":"order","relayTs":...,"relayPayload":"<原始协议JSON>"}
```

外面包一层是为了让接收端**区分谁发的**，避免自己发的消息被自己处理。

### topic 设计

```
xiaowo/<房间码>/msg
```

房间码 6 位，字符集 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`
（去掉了容易看错的 `0/O`、`1/I`、`S/5`）。

### 只配一次是怎么做到的

房间码存 `SharedPreferences`（`relay_room`），生成一次就永久记住。
换 Wi-Fi、重启、覆盖安装都不会丢。

## 三个真实踩到并修掉的坑

写这套东西时遇到了三个问题，都不是靠猜能发现的：

### 坑 1：没等 SUBACK 就发消息，消息丢失

原来是写完 `SUBSCRIBE` 就立刻把状态置为"在线"，调用方可能在这个瞬间发消息，
但 broker 还没完成订阅注册 —— 消息被直接丢掉。

**修法**：必须等 `SUBACK` 才算真的订阅上。

### 坑 2：发布端和订阅端连到不同 broker

公共 broker 之间**不共享消息**。原来的代码两边各自随机选 broker，
大约 2/3 的概率两边不在同一台，消息必然收不到。

**修法**：用房间码做哈希，`brokerFor(room)` 保证同房间永远落在同一台 broker。

实测 3 次全部 PASS（修之前是 PASS 1/3）。

### 坑 3：断线后不重连

公共 broker 会周期性断开连接。

**修法**：`Sub.loop()` 里做退避重连（2s 起，翻倍，上限 30s）。
实测断线后 30 秒内恢复 `在线`。

## 局限（说清楚）

- **QoS0 不保证送达**。网络极差时可能丢。真要保证，得升 QoS1（需要 PUBACK 确认 + 重发队列），目前没做。
- **消息是明文经过公共 broker 的**。所有订阅 `xiaowo/#` 的人理论上都能看到。
  房间码相当于一个弱口令，6 位字符集约 10^9 组合，撞中概率低但**不是零**。
  真在意隐私的话，应该自己做一层加密（换个 AES 密钥，或改用私有 broker）。
- 公共 broker 的可用性不受我们控制。代码里内置了 3 个，但同一房间固定走其中一个。

## 后续值得做的

1. **QoS1 + 重发队列** —— 保证弱网下订单不丢
2. **端到端加密** —— 用房间码派生密钥，AES 加密 payload，公共 broker 看不到明文
3. **扫码配对** —— 把房间码做成二维码，省掉手输 6 位
4. **本地缓存未送达** —— 断了以后把订单存下来，重连自动补发
