# 保活：默认开、不可关、持续自检

## 变化（v3.7）

| | v3.6 及以前 | v3.7 起 |
|---|---|---|
| 保活开关 | 用户可以关 | **没有开关，永远开** |
| 后台隐藏 | 可关 | 固定开（只影响通知文案） |
| 一像素窗 | 可关 | 有权限就立着 |
| 检查时机 | 仅 onCreate | onCreate + 每次 onResume + 每 5 分钟 |
| 状态显示 | 存下来的偏好 | **实时真状态** |

## 为什么删掉开关

原来做开关是为了「不想要常驻通知的人可以关掉」。但实测结论很干脆：

> 保活一停，接单端退到后台几秒，8765 端口就不再应答。
> 点单端只能一直超时，报「没连上张老师」。

也就是说：**关掉这个开关不是"省点资源"，是把 App 弄坏**。
而用户在点的时候并不知道这一点——他以为自己在调"安静一点"。

所以现在的语义：它不是一个偏好，而是运行前提。跟权限一个待遇：
默认开、自动维持、掉了自己修。

## 检查哪些东西

`Keep.sync(activity, isRecv, hint)` —— 幂等，启动/回前台都能调：

1. **前台服务**（`KeepAlive`）
   无条件 `startForegroundService`。服务内部对重复 start 幂等。
2. **一像素悬浮窗**（`PixelKeeper`）
   有 `SYSTEM_ALERT_WINDOW` 就立起来；没权限返回「需要用户去开」。
3. **无障碍截屏**（`ShotService`）
   由 `PermissionGate` 单独处理（见 [silent-shot.md](./silent-shot.md)）。

`Keep.heal(context)` —— 只做**代码能自己修**的部分，不打扰用户，
由 `Keep.startWatchdog()` 挂的 5 分钟定时器调用：

```java
// 每 5 分钟
KeepAlive.start(...);                    // 服务掉了就拉起来
if (能悬浮窗 && !PixelKeeper.isRunning()) PixelKeeper.start(...);
```

## 三个实现细节（都是踩出来的）

**1. 服务状态不能靠 `ActivityManager.getRunningServices()`**

Android 8+ 只返回本应用的服务，看似够用；但实测在 Android 17 的 vivo 上，
对非 debuggable 的 App 直接返回空列表 —— 界面永远显示「没在跑」，误导用户。

改成 `KeepAlive` 里的进程内 `volatile boolean running`：
服务就在本进程，进程没了变量也就没了，语义天然一致。

**2. `PixelKeeper.start()` 必须在主线程加 View**

`addView()` 在非主线程抛 `CalledFromWrongThreadException`。
而它会被 `KeepAlive.onStartCommand` 调用（线程不确定），也会被定时器调用。
现在 `start()` 内部自己判断 `Looper`，不在主线程就 `post` 过去。

**3. 旧版本存下来的 `false` 要清掉**

`KeepAliveCard.aliveEnabled()` 现在**永远返回 `true`**，是刻意的。
同时 `sync()` 里会 `remove(KEY_ALIVE / KEY_HIDE)`，
把老安装里"用户曾经关过"的痕迹清掉，避免以后有人读这两个键被误导。


## 仍然开不了的（系统边界，无解）

vivo / 小米 / OPPO 的这几个白名单项**没有任何公开 API 能静默打开**，
App 能做的只有把用户送到那个页面：

- 自启动
- 允许后台高耗电
- 锁屏显示 / 后台弹出界面

卡片底部有「去系统设置开这些」按钮跳 App 详情页。
